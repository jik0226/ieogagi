# 보안 점검 도구 사용법

> 2026-10-11 분담 변경: 도구 실행·1차 분류는 팀장이 AI 코딩 도구로 하고, 최종 판단도 팀장이 한다. 이 문서는 누구든 도구를 직접 돌려 볼 때 쓰는 안내서다.

> 심사는 정적 분석 도구로 우리 소스를 검사해 **빌드 라인당 보안약점 수**로 점수를 낸다. 같은 종류의 도구를 우리가 먼저 돌려 0건으로 만드는 것이 이 문서의 목적이다.
> 항목별 점검은 [49항목_체크리스트.md](49항목_체크리스트.md), 예외 기록은 [예외_대장.md](예외_대장.md)에 적는다.

## 1. 한눈에 보기

| 도구 | 무엇을 찾나 | 대상 | 인터넷 |
|---|---|---|---|
| ruff | 코드 품질 + 보안 규칙(`S`=bandit 계열, `T20`=print, `BLE`=광범위 except, `ERA`=주석 처리된 코드, `TRY` 등) | `backend/` 전체 | 불필요 |
| bandit | 파이썬 보안약점(SQL 조립, 약한 해시, 하드코드 비밀번호, `shell=True` 등) | `backend/app` | 불필요 |
| semgrep 자체 규칙 | 이어가기 전용 규칙 26개: 백엔드 16개 + 인가 누락 규칙(`fastapi-authz.yml`) + 프론트 9개(`frontend.yml`). KISA 49항목에 직접 대응 | `backend/app`, `frontend/src` | 불필요 |
| semgrep 공식 팩 | `p/python`, `p/secrets`, `p/owasp-top-ten`(백엔드), `p/javascript`, `p/react`, `p/secrets`(프론트) | `backend/app`, `frontend/src` | 필요 |
| pip-audit | 파이썬 의존성의 알려진 취약점(CVE) — SW 공급망 보안 | `backend/requirements.lock` | 필요 |
| npm audit | 프론트 의존성의 알려진 취약점(운영 의존성만) | `frontend/` | 필요 |
| gitleaks | 저장소 전체의 비밀값(키·토큰·비밀번호) 유출. `make secrets-scan`, push 전에 실행 | 저장소 전체 | 불필요 |
| eslint | 프론트 코드 규칙(`react/no-danger`, `no-eval`, `no-console`, `no-alert`, 브라우저 저장소·`Math.random`·`document.cookie`·innerHTML 대입·문자열 타이머 금지, eslint-plugin-security) | `frontend/` | 불필요 |

## 2. 처음 한 번만 (환경 준비)

필요한 프로그램: `git`, `make`, `uv`, `node`(26 이상), `npm`. macOS는 `brew install uv node`면 된다.

```bash
make setup      # backend/.venv 만들기 + 해시 고정 의존성 설치 + 프론트 npm ci
```

`make`를 쓸 수 없는 환경(Windows 등)이면 [5. 도구를 하나씩 실행](#5-도구를-하나씩-실행)의 명령을 직접 입력한다. 모든 명령은 **저장소 맨 위 폴더**에서 실행한다.

## 3. 실행 방법

| 상황 | 명령 | 걸리는 시간 | 비고 |
|---|---|---|---|
| 1차 점검·재점검(전체) | `make security` | 1~2분 | 인터넷 필요. 모든 도구 실행 |
| 푸시 전 빠른 확인 | `make security-quick` | 수 초 | 인터넷 불필요. ruff + bandit + semgrep 자체 규칙만 |
| 자체 규칙 자가 테스트 | `make semgrep-test` | 수 초 | 규칙 파일을 고쳤을 때 |

- 한 도구가 실패하거나 건수가 있어도 나머지 도구는 계속 돈다. 마지막에 요약 표가 나온다.
- 인터넷이 없으면 공식 팩·pip-audit·npm audit은 `SKIP`으로 표시된다(실패는 아니지만 통과로 세지도 않는다 — 종료 코드 4).
- 종료 코드: 0 = 모든 단계를 돌렸고 건수 없음, 1 = 건수 있음, 2 = 옵션 오류, 3 = 도구 오류(결과를 알 수 없음, 건수가 함께 있어도 3), 4 = 건수는 없지만 건너뛴 도구가 있어 결과 불완전(우선순위 3 > 1 > 4 > 0, 4가 나오면 SKIP 줄의 도구를 갖춰 다시 돌린다). 건수가 있으면 `make`가 `Error 1`을 보여 주는 것이 정상이고, `Error 3`이면 ERROR 줄의 `*.stderr.log`부터 본다.

요약 표 예시:

```
TOOL                   STATUS COUNT  NOTE
ruff                   FOUND  6      ruff.json
bandit                 OK     0      bandit.json
semgrep(custom)        OK     0      semgrep-custom.json
...
```

| STATUS | 뜻 |
|---|---|
| OK | 0건 |
| FOUND | 1건 이상 — 리포트를 열어 판정 |
| ERROR | 도구가 제대로 돌지 못함 — 같은 폴더의 `*.stderr.log` 확인. 정상 범위 밖 종료 코드(ruff·bandit·pip-audit·npm audit은 0·1, Semgrep은 0만 정상), JSON이 아니거나 필수 필드가 없는 보고서, 오류 항목(Semgrep `errors`는 `warn` 수준 구문 분석 오류까지 모두, bandit 스캔 실패 파일, npm `error`), 발견 0건인데 exit 1이면 모두 ERROR다(0건으로 세지 않는다) |
| SKIP | 도구 없음·오프라인·프론트 없음 등으로 건너뜀 (사유가 NOTE에 있음). 통과가 아니므로 다른 줄이 모두 OK여도 종료 코드는 4 |

## 4. 리포트는 어디에 생기나

`security/reports/<YYYY-MM-DD_HHMM>/` (가장 최근 것은 `security/reports/latest`). 이 폴더는 git에 올라가지 않는다.

| 파일 | 내용 |
|---|---|
| `summary.txt` | 요약 표 + 분석한 코드 줄 수(bandit 기준) |
| `ruff.json` | ruff 결과 |
| `bandit.txt` / `bandit.json` | bandit 결과(읽기 쉬운 것은 txt) |
| `semgrep-custom.json` | 자체 규칙 결과 |
| `semgrep-registry-backend.json`, `semgrep-registry-frontend.json` | 공식 팩 결과 |
| `pip-audit.json`, `npm-audit.json`, `npm-lint.txt` | 의존성·eslint 결과 |
| `*.stderr.log` | 각 도구가 낸 경고·오류 메시지 |

JSON은 읽기 불편하므로 **같은 명령을 JSON 옵션 없이 다시 실행**하면 사람이 읽기 좋은 글자로 나온다(5절). semgrep JSON만 간단히 보고 싶다면:

```bash
python3 -I -c "
import json, sys
for r in json.load(open(sys.argv[1]))['results']:
    print(r['path'] + ':' + str(r['start']['line']), r['check_id'].split('.')[-1])
" security/reports/latest/semgrep-custom.json
```

## 5. 도구를 하나씩 실행

```bash
# 파이썬 정적 분석
backend/.venv/bin/ruff check backend
backend/.venv/bin/bandit -r backend/app -c backend/pyproject.toml

# 이어가기 자체 Semgrep 규칙 (인터넷 불필요)
backend/.venv/bin/semgrep --config security/semgrep --metrics=off backend/app frontend/src

# Semgrep 공식 팩 (실행할 때 내려받음, 인터넷 필요)
backend/.venv/bin/semgrep --config p/python --config p/secrets --config p/owasp-top-ten --metrics=off backend/app
backend/.venv/bin/semgrep --config p/javascript --config p/react --config p/secrets --metrics=off frontend/src

# 의존성 취약점
backend/.venv/bin/pip-audit -r backend/requirements.lock
npm --prefix frontend audit --omit=dev

# 프론트 lint
npm --prefix frontend run lint

# 자체 Semgrep 규칙의 테스트 (규칙을 고쳤을 때)
make semgrep-test
```

`semgrep --test security/semgrep/`처럼 폴더 하나만 주면 `tests/` 하위 폴더의 테스트를 찾지 못해 "No unit tests found"가 나온다. 반드시 `make semgrep-test`(= `--test --config security/semgrep security/semgrep/tests`)를 쓴다.

## 6. 결과 판정 (triage)

FOUND가 나오면 건마다 아래 순서로 본다.

1. **위치를 연다.** 리포트의 `파일:줄`을 열고 어떤 규칙이 잡았는지 확인한다. 규칙 이름에서 KISA 항목을 찾는다(표는 7절, 체크리스트 번호는 49항목 표).
2. **실제 문제인가?** "이 코드가 정말 그 약점(예: SQL 삽입, 정보 노출)을 만들 수 있는가"를 묻는다. 모르겠으면 리드에게 묻는다. 혼자 오탐이라고 단정하지 않는다.
3. **진양성**(실제 문제) → GitHub 이슈로 수정 요청한다.
   - 제목: `[보안] <KISA 항목명> <파일:줄>`
   - 본문: 도구·규칙 이름, 코드 위치, 왜 문제인지 한 줄, 제안하는 수정 방향, 체크리스트 번호
   - 담당자가 고치면 `make security-quick`으로 다시 확인하고 체크리스트의 **조치·사유**에 이슈·커밋 번호를 적는다.
4. **오탐**(문제가 아닌데 잡힘) 또는 **수용**(알고 있지만 두기로 함) → [예외 대장](예외_대장.md)에 기록한다. 코드를 바꿔 도구를 피할 수 있으면 그쪽이 낫다(예: 변수 이름 바꾸기).

### 줄 단위 예외 처리 (inline suppression)

아래 세 가지 주석은 **허용하지만 조건이 있다**: (1) 바로 위 줄에 **영어로 이유**를 쓰고, (2) 예외 대장에 같은 번호의 항목이 있어야 한다. 둘 중 하나라도 없으면 쓰지 않는다.

```python
# Exception ledger #3 (false positive): fixture value, not a real credential.
password = "example-only"  # nosec B105  # noqa: S105  # nosemgrep: ieogagi-no-hardcoded-secret
```

| 도구 | 형식 | 비고 |
|---|---|---|
| ruff | `# noqa: S105` | 규칙 번호를 반드시 쓴다 |
| bandit | `# nosec B105` | 규칙 번호를 반드시 쓴다 |
| semgrep | `# nosemgrep: ieogagi-no-hardcoded-secret` | 규칙 ID를 반드시 쓴다. 여러 줄 규칙(`try/except` 등)은 **첫 줄**(`try:`) 또는 그 바로 윗줄에 둔다 |

금지:

- 번호·ID 없는 `# nosec`, `# noqa`, `# nosemgrep`
- 파일 전체를 끄는 설정, `backend/pyproject.toml`의 `ignore`·`exclude_dirs`를 늘리는 일, 규칙 파일(`security/semgrep/*.yml`)을 고쳐 건수를 줄이는 일 → 리드 승인 후에만

## 7. 자체 Semgrep 규칙 목록

모든 규칙은 `security/semgrep/`에 있고 테스트는 `security/semgrep/tests/`에 있다. 메시지는 한국어·영어를 함께 담았다.

| 규칙 ID | 잡는 것 | KISA 항목 | 파일 |
|---|---|---|---|
| `ieogagi-no-eval-exec` | 리터럴이 아닌 값의 `eval`·`exec`·`compile(..,"exec")`·`__import__` | 코드 삽입 | `injection.yml` |
| `ieogagi-no-raw-sql-format` | `text(f"..")`, `"..".format/%/+` 로 만든 SQL, `.execute(f"..")` | SQL 삽입 | `injection.yml` |
| `ieogagi-no-shell` | `shell=True`, `os.system`, `os.popen` | 운영체제 명령어 삽입 | `injection.yml` |
| `ieogagi-no-ssrf-redirect` | 리터럴이 아닌 URL의 `RedirectResponse` | 신뢰되지 않는 URL 주소로 자동접속 연결 | `injection.yml` |
| `ieogagi-no-broad-except` | `except Exception`·`BaseException`·맨몸 `except:` | 부적절한 예외 처리 | `error-handling.yml` |
| `ieogagi-no-empty-except` | `pass`·`...`·`continue`뿐인 except | 오류 상황 대응 부재 | `error-handling.yml` |
| `ieogagi-no-exception-leak` | 예외 문구·traceback을 응답에 담기 | 오류 메시지 정보 노출 | `error-handling.yml` |
| `ieogagi-no-print` | `print`·`pprint`·`breakpoint`·`pdb.set_trace` | 제거되지 않고 남은 디버그 코드 | `debug-code.yml` |
| `ieogagi-no-main-block` | `if __name__ == "__main__":` | 제거되지 않고 남은 디버그 코드 | `debug-code.yml` |
| `ieogagi-no-debug-mode` | `FastAPI(debug=True)`, `uvicorn.run(reload=True)`, DEBUG 로그 레벨 고정 | 제거되지 않고 남은 디버그 코드 | `debug-code.yml` |
| `ieogagi-no-insecure-random` | `random` 모듈 import | 적절하지 않은 난수 값 사용 | `crypto-secrets.yml` |
| `ieogagi-no-weak-hash` | `hashlib.md5`·`sha1`, 비밀번호에 `sha256` 직접 사용 | 취약한 암호화 알고리즘 사용 / 솔트 없이 일방향 해시 | `crypto-secrets.yml` |
| `ieogagi-no-hardcoded-secret` | `password`·`secret`·`token`·`api_key`·`private_key` 이름에 문자열 리터럴 대입(빈 문자열 제외) | 하드코드된 중요정보 | `crypto-secrets.yml` |
| `ieogagi-no-tls-verify-off` | `verify=False`, 검증 없는 SSL 컨텍스트 | 부적절한 인증서 유효성 검증 | `crypto-secrets.yml` |
| `ieogagi-no-unsafe-deserialization` | `pickle`·`marshal`·`shelve`·안전하지 않은 `yaml.load` | 신뢰할 수 없는 데이터의 역직렬화 | `unsafe-api.yml` |
| `ieogagi-no-tempfile-mktemp` | `tempfile.mktemp` | 경쟁조건: 검사 시점과 사용 시점 | `unsafe-api.yml` |
| `ieogagi-fe-dom-xss-sink` | `dangerouslySetInnerHTML`, innerHTML·outerHTML 대입, `insertAdjacentHTML`, `document.write`, `createContextualFragment` | 크로스사이트 스크립트 | `frontend.yml` |
| `ieogagi-fe-dynamic-code` | `eval`, `new Function`, 문자열을 넘긴 `setTimeout`·`setInterval` | 코드 삽입 | `frontend.yml` |
| `ieogagi-fe-debug-code` | `console.*`, `alert`·`confirm`·`prompt`, `debugger` | 제거되지 않고 남은 디버그 코드 | `frontend.yml` |
| `ieogagi-fe-browser-storage` | `localStorage`·`sessionStorage`·`indexedDB`·`document.cookie` | 사용자 하드디스크에 저장되는 쿠키를 통한 정보노출 | `frontend.yml` |
| `ieogagi-fe-open-redirect` | 리터럴 내부 경로가 아닌 값으로 `location` 대입·`assign`·`replace`·`window.open` | 신뢰되지 않는 URL 주소로 자동접속 연결 | `frontend.yml` |
| `ieogagi-fe-weak-random` | `Math.random()` | 적절하지 않은 난수 값 사용 | `frontend.yml` |
| `ieogagi-fe-postmessage-wildcard` | `postMessage(.., "*")` | 부적절한 인가 | `frontend.yml` |
| `ieogagi-fe-hardcoded-endpoint` | 절대 http(s) URL·IPv4 문자열(XML 네임스페이스 제외). `frontend/src`만 검사 — `vite.config.js`의 개발용 프록시 기본값은 빌드에 들어가지 않아 제외 | 하드코드된 중요정보 | `frontend.yml` |
| `ieogagi-fe-empty-catch` | 빈 catch 블록(주석만 있어도)·빈 `.catch` 처리기, `finally` 포함. 2라운드 진단 04.02 조치로 추가(11/05) | 오류 상황 대응 부재 | `frontend.yml` |

주의할 오탐 패턴:

- `ieogagi-no-hardcoded-secret`는 이름만 보고 잡는다. `token_type = "bearer"`처럼 비밀이 아닌 값도 걸린다. 심사 도구도 비슷하게 잡으므로 **변수 이름을 바꾸는 쪽**을 먼저 시도한다(예: `token_type` → `auth_scheme`).
- `ieogagi-no-print`는 `print`를 무조건 잡는다. 로그는 `logging`을 쓴다.

### 규칙을 고치거나 추가할 때

1. `security/semgrep/*.yml`에 규칙을 추가하고 `metadata`에 `kisa-category`, `kisa-item`, `cwe`를 쓴다.
2. 같은 이름의 `security/semgrep/tests/<파일명>.py`에 잡혀야 하는 줄 위에 `# ruleid: <규칙ID>`, 잡히면 안 되는 줄 위에 `# ok: <규칙ID>` 주석을 쓴다.
3. `make semgrep-test`가 통과하고 `backend/.venv/bin/semgrep --metrics=off --validate --config security/semgrep/`에 오류가 없어야 한다.

Semgrep 규칙을 쓰다 겪기 쉬운 함정:

- 테스트에서 `x = "..."` 처럼 변수에 리터럴을 넣고 쓰면 Semgrep이 값을 따라가서(상수 전파) 리터럴로 취급한다. 테스트 값은 **함수 인자**로 받는다.
- YAML에서 패턴에 `: `이 들어 있거나 `"`로 시작하면 작은따옴표로 감싸야 한다.
- `metavariable-regex`는 문자열 처음부터 일치를 보므로 앞에 `.*`를 붙여야 부분 일치가 된다.

## 9. 반드시 지킬 것

- **Semgrep 공식(레지스트리) 규칙은 실행 시점에 내려받아 쓰고, 저장소에 복사하지 않는다.** Semgrep Rules License는 규칙의 재배포를 금지한다. `--config p/...` 형태로만 쓰고, 규칙 파일을 내려받아 `security/` 아래에 넣거나 커밋하지 않는다. 우리가 직접 쓴 `security/semgrep/*.yml`은 자유롭게 공개해도 된다.
- 공식 팩 결과 JSON에는 공식 규칙의 설명 문구가 들어 있다. `security/reports/`는 `.gitignore`에 있으니 커밋하지 말고, 발표 자료에는 건수·항목명 위주로 옮긴다.
- 예외 처리 주석(`# nosec`, `# noqa`, `# nosemgrep`)은 6절 조건(영어 이유 주석 + 예외 대장 번호)을 지킨다.
- **제출 소스 범위 확인(리드와 상의):** `security/semgrep/tests/*.py`에는 규칙을 시험하려고 **일부러 취약하게 쓴 코드**(`eval`, `print`, 하드코드 비밀번호 등)가 들어 있다. 심사 도구가 저장소 전체를 소스로 검사하면 이 파일들이 약점으로 계산될 수 있으므로, 제출 소스에서 제외할 수 있는지(또는 제출 전 별도 보관) 확인한다.

## 10. 자주 겪는 문제

| 증상 | 원인·해결 |
|---|---|
| `backend/.venv/bin/ruff: No such file` | `make setup`을 아직 안 했다 |
| 요약 표에 `SKIP 오프라인` | 인터넷이 없다. 공식 팩·pip-audit·npm audit은 인터넷이 되는 곳에서 다시 실행 |
| `npm-lint SKIP node_modules 없음` | `npm --prefix frontend ci` 실행 |
| `semgrep(custom) ERROR` | `security/reports/latest/semgrep-custom.stderr.log`를 열어 규칙 파일 YAML 오류가 있는지 확인 후 `backend/.venv/bin/semgrep --metrics=off --validate --config security/semgrep/` |
| pre-commit 훅이 파일을 고쳐 버림 | `end-of-file-fixer`, `trailing-whitespace`는 자동 수정 훅이다. 작업을 커밋(또는 stash)한 깨끗한 상태에서 `pre-commit run --all-files`를 실행하고, 바뀐 파일은 확인 후 커밋한다. `pre-commit install` 여부는 리드가 정한다 |
